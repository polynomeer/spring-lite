# Visual Lab UX And Visualization Improvement Plan

이 문서는 현재 `visual-lab`과 `visual-lab-app`이 가진 사용성 문제를 정리하고, `Run` 실행 이후 결과를 더 직관적인 다이어그램으로 읽을 수 있도록 개선하는 작업 계획을 정의한다.

기준 날짜는 2026-08-31이다.

## 1. 왜 이 문서가 필요한가

현재 `visual-lab`은 기능 자체보다도 "무엇을 보기 위한 화면인가", "어떤 순서로 조작하고 읽어야 하는가", "실행 결과를 어떤 관점으로 해석해야 하는가"가 첫 화면에서 충분히 드러나지 않는다.

특히 아래 문제가 크다.

- 화면이 `trace`, `provider`, `runtime` 같은 내부 구현 용어를 먼저 노출한다.
- 랩 선택, 시나리오 선택, 실행 상태, 마지막 실행 상태가 동시에 보여서 첫 사용자에게 부담이 크다.
- `Run` 이후 결과가 텍스트 중심 요약에 치우쳐 있어, "흐름이 어디서 갈렸는지"를 한눈에 읽기 어렵다.
- 정적 시뮬레이션과 라이브 실행의 차이는 존재하지만, 그것이 학습 목적에 어떤 차이를 만드는지 명확히 설명되지 않는다.

따라서 다음 단계는 기능 추가보다 먼저, **학습 목적을 명확히 드러내는 정보 구조**와 **실행 결과를 즉시 해석할 수 있는 시각화 구조**를 만드는 데 있어야 한다.

## 2. 개선 목표

이번 개선의 목표는 아래 네 가지다.

1. 사용자가 첫 화면에서 "이 랩으로 어떤 질문에 답할 수 있는지"를 바로 이해한다.
2. 사용자가 무엇을 선택했고, 무엇이 실행되었고, 지금 무엇을 보고 있는지 헷갈리지 않는다.
3. `Run` 이후 결과가 텍스트 목록이 아니라 흐름도, 레인 다이어그램, 상태 변화도로 읽힌다.
4. 코드/문서/테스트 연결은 유지하되, 핵심 결과 해석을 방해하지 않도록 후순위로 배치한다.

## 3. UX 원칙

이번 개선은 아래 원칙을 따른다.

### 3.1 질문 중심 진입

랩 이름보다 질문을 먼저 보여준다.

예:

- "트랜잭션은 어디서 시작되고 어디서 롤백되는가"
- "컨트롤러 요청은 어느 단계에서 400/404/500으로 갈리는가"
- "빈은 언제 프록시로 감싸지고 언제 원본으로 남는가"

### 3.2 실행 전과 실행 후를 분리

실행 전 화면은 "무엇을 검증할지 고르는 단계"에 집중한다.

실행 후 화면은 "무엇이 일어났는지 읽는 단계"에 집중한다.

이 둘을 한 패널 안에 중첩해서 보여주지 않는다.

### 3.3 결과 해석 우선

실행 결과는 먼저 아래 순서로 보여준다.

1. 이번 실행의 핵심 결론 1문장
2. 어디서 분기되었는지 보여주는 시각화
3. 단계별 상세 데이터
4. 관련 코드/문서/테스트

### 3.4 점진적 공개

처음부터 모든 상태를 노출하지 않는다.

- 초행 사용자는 핵심 요약과 메인 다이어그램만 본다.
- 더 깊게 보고 싶을 때 `step`, `lane`, `snapshot`, `references`를 펼친다.

이는 UX 기준상 progressive disclosure 원칙에 맞다. 또한 결과가 없거나 아직 실행되지 않았을 때 빈 화면 대신 다음 행동을 제안해야 한다.

## 4. 현재 문제 진단

## 4.1 첫 화면의 목적이 불명확함

현재 첫 화면은 `Spring Lite Visual Lab`와 실행 상태를 먼저 보여주지만, 사용자는 이 화면으로 무엇을 배울 수 있는지 즉시 파악하기 어렵다.

문제:

- 제목은 크지만 학습 목표는 작다.
- 내부 상태 배지가 상단의 의미를 잡아먹는다.
- 추천 시작점과 질문별 진입이 기본 레이아웃에 흡수되지 못했다.

개선 방향:

- 히어로 영역에 "이 화면으로 답할 수 있는 질문" 3개를 고정 배치
- 첫 진입 시 추천 시작 시나리오를 하나만 강조
- 모드 설명은 부제보다 짧은 인라인 가이드로 축소

## 4.2 선택과 실행 상태가 과도하게 드러남

현재는 `selected request`, `last executed`, `selection changed`, `pipeline pending`이 함께 보여서 사용자가 "왜 아직 실행이 안 됐는가"를 계속 해석해야 한다.

문제:

- 초행 사용자는 내부 상태 모델을 이해해야만 화면을 읽을 수 있다.
- 같은 정보가 여러 곳에 중복된다.
- 실행 버튼의 대상이 시각적으로 충분히 강하게 묶여 있지 않다.

개선 방향:

- 실행 전 패널에서 현재 선택만 보여준다.
- 실행 후 패널에서 마지막 실행 결과만 보여준다.
- 둘 사이 차이는 `선택 변경됨. 다시 실행 필요` 같은 한 줄 알림으로만 노출한다.

## 4.3 결과 패널이 읽기보다 탐색을 요구함

현재 결과는 탭 구조와 상세 정보가 풍부하지만, 무엇부터 읽어야 하는지 안내가 약하다.

문제:

- `overview`, `flow`, `references`가 모두 동등하게 보인다.
- 핵심 결론과 다이어그램이 하나의 학습 흐름으로 묶이지 않는다.
- `references`의 중요도가 실제 해석보다 앞에 보일 수 있다.

개선 방향:

- 결과 상단에 `이번 실행에서 봐야 할 것` 카드 추가
- 메인 다이어그램 아래에 `이 단계에서 분기됨`, `여기서 rollback 발생`, `이 bean이 proxy로 노출됨` 같은 callout 추가
- 참고 자료는 접을 수 있는 보조 탭으로 이동

## 5. 새 정보 구조 제안

권장 레이아웃은 아래와 같다.

### 5.1 Step A. 질문 선택

첫 줄에서 랩 이름이 아니라 질문 카드를 보여준다.

예:

- Transaction rollback trace
- MVC error branch trace
- Container bootstrap trace
- Spring Lite vs Spring comparison

각 카드는 아래 정보를 가진다.

- 질문 한 줄
- 관련 랩 이름
- 추천 난이도
- static / live 지원 상태

### 5.2 Step B. 시나리오 조합

질문을 고르면 그에 맞는 시나리오와 실행 모드만 보여준다.

예:

- 시나리오: `create`, `validation`, `rollback`
- 모드: `static`, `live`

이 단계에서는 아직 결과 패널을 크게 보여주지 않는다.

### 5.3 Step C. 실행

`Run` 버튼은 항상 현재 선택 카드와 시각적으로 붙어 있어야 한다.

버튼 바로 옆에 다음 정보를 둔다.

- 현재 실행 대상
- live 연결 상태
- 마지막 성공 실행 시각

### 5.4 Step D. 결과 읽기

실행이 끝나면 결과 영역을 아래 순서로 보여준다.

1. 핵심 결론 요약
2. 메인 다이어그램
3. 단계별 상세
4. 참고 코드/문서/테스트

## 6. Run 이후 추가할 시각화

이번 개선의 핵심은 `Run` 결과를 더 시각적으로 읽게 만드는 것이다.

## 6.1 Execution Path Diagram

가장 먼저 추가할 다이어그램이다.

역할:

- 이번 요청이 어떤 노드를 통과했는지
- 어디서 성공/실패/예외 분기가 일어났는지
- 현재 시나리오에서 실제로 밟은 경로만 무엇인지

형태:

- 좌에서 우로 진행하는 노드 기반 흐름도
- 분기 노드는 diamond 또는 split node
- 실제로 실행된 경로는 강조
- 실행되지 않은 경로는 희미하게 유지

적용 대상:

- `example-flow`
- `playground`의 MVC branch

## 6.2 Lane Timeline Diagram

현재의 step/lane 정보를 더 명시적인 다이어그램으로 강화한다.

역할:

- MVC / Service / Tx / JDBC / Exception Resolver 같은 레인 간 흐름 표현
- begin / commit / rollback 같은 경계 이벤트를 시간 순으로 표시
- 어느 레인에서 시간이 오래 걸렸는지 또는 이벤트가 몰렸는지 표시

형태:

- 세로 레인 + 가로 시간축
- step hover 시 관련 레인 강조
- 특정 step 선택 시 전후 관계를 연결선으로 표시

적용 대상:

- `example-flow`
- `playground` AOP/Tx

## 6.3 State Transition Diagram

컨테이너와 빈 생명주기를 읽을 때 적합한 시각화다.

역할:

- BeanDefinition -> instantiate -> populate -> post-process -> init -> proxy expose -> destroy 등록
- singleton/prototype 차이 표현
- raw target과 exposed bean의 분리 표현

형태:

- 상태 노드 전이 다이어그램
- proxy wrapping이 일어나는 지점 강조
- destroy callback 등록 여부를 side branch로 표시

적용 대상:

- `container`

## 6.4 Comparison Diff Diagram

실제 Spring과 `spring-lite`를 비교할 때 필요한 시각화다.

역할:

- 같은 시나리오에서 공통 단계와 차이 단계 분리
- 어느 부분이 축소 구현인지 표시
- 코드 대응 문서와 연결

형태:

- 좌우 대칭 비교
- 공통 구간은 가운데 브리지로 연결
- 차이 구간은 색과 캡션으로 표시

적용 대상:

- `comparison`

## 6.5 Runtime Health Strip

보조 시각화지만 라이브 실행에서 중요하다.

역할:

- live endpoint 연결 상태
- 마지막 trace 수신 여부
- fallback trace 사용 여부
- 현재 표시 중인 결과가 static인지 live인지 즉시 구분

형태:

- 상단 얇은 상태 바
- 색상과 아이콘으로 상태만 짧게 표시
- 본문 설명은 tooltip 또는 세부 패널로 이동

## 7. 다이어그램과 기존 데이터 구조의 연결

새 시각화는 기존 `LabTrace`를 버리지 않고 그 위에 어댑터를 추가하는 방향이 적합하다.

권장 구조:

- `LabTrace`
  - 원본 단계, 메트릭, 레퍼런스, 스냅샷 유지
- `TraceVisualizationAdapter`
  - `LabTrace`를 다이어그램 노드/엣지/레인 이벤트로 변환
- `TraceNarrativeAdapter`
  - 이번 실행의 핵심 결론 1문장과 경고/의미/다음 행동 생성

즉, 원본 trace는 데이터 계약으로 유지하고, 시각화는 어댑터 계층에서 별도로 조립한다.

## 8. 권장 구현 순서

이번 개선은 아래 순서가 현실적이다.

### Phase 1. Information Architecture Reset

범위:

- 첫 화면 카피 재작성
- 질문 기반 시작 카드 추가
- 선택/실행 상태 중복 제거
- 결과 패널 상단에 핵심 결론 카드 추가

완료 기준:

- 초행 사용자도 "무엇을 고르고 무엇을 읽는지"를 10초 안에 이해할 수 있다.

### Phase 2. Execution Path Diagram

범위:

- `example-flow` 우선
- `create`, `validation`, `rollback`, `service-error`, `not-found` 시나리오 다이어그램화
- 실제 실행 경로 강조, 미실행 경로 비활성 표현

완료 기준:

- `Run` 후 텍스트를 읽지 않아도 어디서 분기되었는지 다이어그램으로 이해할 수 있다.

### Phase 3. Lane Timeline Upgrade

범위:

- 레인 시각 표현 강화
- hover/select에 따른 연관 step 강조
- rollback, exception, response write 같은 핵심 이벤트 마커 추가

완료 기준:

- step/lane 패널이 단순 목록이 아니라 시간적 관계를 드러내는 분석 뷰가 된다.

### Phase 4. Container State Diagram

범위:

- `bootstrap-full`
- `lifecycle-proxy`
- bean lifecycle와 proxy exposure를 상태 전이도로 표현

완료 기준:

- 컨테이너 내부 동작을 텍스트가 아닌 상태 전이로 이해할 수 있다.

### Phase 5. Comparison Diff Diagram

범위:

- `di`, `mvc`, `tx` 비교 시나리오
- 공통점/차이점/축소점 시각화
- 관련 문서 deep link 연결

완료 기준:

- `spring-lite`와 실제 Spring의 차이가 글이 아니라 구조도로 읽힌다.

### Phase 6. Live Narrative And Replay

범위:

- live 실행 후 핵심 요약 문장 자동 생성
- step-by-step replay
- live fallback과 실제 결과의 차이 명시

완료 기준:

- 라이브 실행이 단순 fetch 결과가 아니라 해석 가능한 학습 세션이 된다.

## 9. 작업 백로그

가까운 작업 단위는 아래와 같다.

1. `visual-lab-app`의 첫 화면 카피와 정보 구조를 재설계한다.
2. 질문 카드 데이터 모델을 추가한다.
3. 결과 패널 상단에 `이번 실행에서 봐야 할 것` 컴포넌트를 추가한다.
4. `example-flow`용 execution path 다이어그램 데이터 어댑터를 만든다.
5. execution path 다이어그램 컴포넌트를 구현한다.
6. `LabTrace`에서 다이어그램 노드/엣지를 만드는 테스트를 작성한다.
7. live/static 상태를 한눈에 구분하는 health strip을 추가한다.
8. `container` 상태 전이 다이어그램의 노드 모델을 설계한다.
9. comparison diff 다이어그램의 공통 스키마를 정의한다.
10. 관련 README와 사용 가이드를 갱신한다.

## 11. 최종 권고

현재 `visual-lab`의 가장 큰 문제는 기능 부족보다 해석 구조 부족이다.

따라서 우선순위는 아래처럼 두는 것이 맞다.

1. 첫 화면에서 학습 목적을 바로 이해하게 만든다.
2. `Run` 결과를 텍스트보다 다이어그램으로 먼저 읽게 만든다.
3. 코드/문서/테스트 연결은 그 다음 깊이로 유지한다.
4. 라이브 기능은 더 늘리되, 해석 UX가 정리된 뒤 확장한다.

즉, 다음 단계의 핵심은 "더 많은 기능"이 아니라 **더 좋은 학습 흐름과 더 강한 시각적 설명력**이다.
