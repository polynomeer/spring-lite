# Part 6 Draft

## Part 6. JDBC, 예제 앱, Boot 계층으로 완성한다

Part 6은 지금까지 만든 조각들을 실제 애플리케이션 형태로 엮는 단계다. 컨테이너와 AOP, MVC가 각각 따로 이해되더라도, 데이터 접근과 애플리케이션 실행 모델까지 연결되지 않으면 독자는 아직 "프레임워크가 완성되었다"는 감각을 얻기 어렵다. 이 파트는 `JdbcTemplate`, 예제 앱, `SpringLiteApplication`, 테스트 지원을 통해 그 감각을 만들어준다.

## Chapter 21. `JdbcTemplate`과 데이터 접근 추상화

### 21.1 JDBC의 반복과 추상화의 필요

순수 JDBC 코드는 강력하지만 반복이 많다. 커넥션을 얻고, statement를 만들고, 파라미터를 바인딩하고, 결과를 읽고, 예외를 처리하고, 자원을 닫는 코드가 계속 등장한다. SQL은 다르지만 주변 의식은 거의 같은 경우가 많다. 이런 구조는 템플릿 패턴의 전형적인 적용 대상이다.

`spring-lite`의 `JdbcTemplate`은 이 반복 구조를 줄이는 최소 추상화다. 개발자는 SQL과 결과 매핑이라는 가변 부분만 제공하고, 나머지 자원 관리와 오류 처리, 트랜잭션 연계는 프레임워크가 담당한다.

### 21.2 `RowMapper`와 템플릿 패턴

`RowMapper`는 결과 집합을 도메인 객체로 바꾸는 책임을 콜백으로 분리한다. 이 분리는 단순 구현 편의가 아니라 설계적 의미가 있다. 프레임워크는 반복적인 흐름을 보장하고, 애플리케이션은 도메인 해석만 집중한다. 이 패턴은 컨테이너와 AOP에서 보았던 "불변 골격 + 가변 전략"이라는 Spring의 전형적인 설계 감각과도 연결된다.

### 21.3 트랜잭션과 커넥션 재사용

이 장에서 빠뜨리면 안 되는 포인트는 JDBC 추상화가 트랜잭션과 분리되지 않는다는 점이다. 같은 트랜잭션 문맥 안에서는 동일 커넥션을 재사용해야 한다. 그렇지 않으면 선언형 트랜잭션이 의미를 잃는다. 따라서 `JdbcTemplate`은 단순 SQL 편의 도구가 아니라 트랜잭션 인프라와 맞물린 데이터 접근 계층이다.

## Chapter 22. 예제 앱으로 모든 계층을 연결하기

### 22.1 왜 예제 앱이 필요한가

지금까지의 장들은 각각 특정 계층을 설명하는 데 집중했다. 하지만 독자는 어느 시점에 "그래서 이 모든 것이 한 요청 안에서 어떻게 만나는가"를 보고 싶어진다. 예제 앱은 바로 그 요구를 해결한다. 주문 생성과 조회 같은 단순한 도메인이더라도, 컨트롤러, 서비스, 저장소, 검증, 트랜잭션, JDBC가 모두 한 흐름에 등장한다.

### 22.2 컨트롤러에서 저장소까지 이어지는 길

예제 앱 장에서는 HTTP 요청이 컨트롤러를 거쳐 서비스로 가고, 서비스가 트랜잭션 프록시 안에서 저장소를 호출하고, 저장소가 `JdbcTemplate`으로 SQL을 실행한 뒤 결과가 다시 웹 응답으로 돌아오는 흐름을 끝까지 따라간다. 독자가 이 흐름을 자신의 말로 설명할 수 있다면, 앞선 파트들이 비로소 하나의 구조로 붙기 시작한 것이다.

### 22.3 테스트가 문서가 되는 순간

예제 앱은 단지 데모가 아니라 문서이기도 하다. 어떤 입력이 어떤 검증을 통과하고, 어떤 예외가 어떤 응답으로 변환되며, 어떤 서비스 호출이 트랜잭션 안에서 수행되는지를 테스트가 보여준다. 이 장은 "예제 애플리케이션이 프레임워크 설명의 증거 역할을 한다"는 메시지를 분명히 해야 한다.

## Chapter 23. `SpringLiteApplication`과 Bootstrapping

### 23.1 프레임워크를 실행 가능한 형태로 묶기

사용자는 컨테이너, AOP, MVC, JDBC를 하나씩 직접 조립하고 싶어하지 않는다. 보통은 `run()` 한 줄로 애플리케이션이 시작되기를 원한다. 그래서 부트스트랩 계층이 필요하다. 이 계층은 설정 클래스 인식, 컴포넌트 스캔 시작점 설정, 인프라 빈 등록, 웹 서버 시작, 컨텍스트 생명주기 관리를 한곳에 모은다.

`SpringLiteApplication`은 학습용 규모에서 이 역할을 보여준다. 중요한 것은 코드 양이 아니라, 애플리케이션 시작이 결국 여러 하위 프레임워크를 순서 있게 조립하는 문제라는 사실을 드러내는 데 있다.

### 23.2 `@SpringLiteBootApplication`의 의미

실제 Spring Boot에서 `@SpringBootApplication`이 여러 메타 애너테이션 조합인 것처럼, `spring-lite`도 실행 시작점을 명확히 드러내는 진입 애너테이션을 제공한다. 이 장에서는 메타 애너테이션이 단순 편의 문법이 아니라, "어떤 구성 모델로 애플리케이션을 시작할 것인가"를 선언하는 진입 계약이라는 점을 설명하면 좋다.

### 23.3 실제 Spring Boot와의 거리

실제 Spring Boot는 조건부 자동 설정, starter 생태계, 외부 설정 바인딩, 프로파일, 환경별 조립 등 훨씬 더 큰 문제를 푼다. `spring-lite`는 그 축소판이지만, 축소판이기 때문에 오히려 핵심 구조가 잘 보인다. 이 장은 실제 Boot의 복잡성을 공정하게 이해하는 발판이 된다.

## Chapter 24. 테스트 지원 모듈과 프레임워크 검증 전략

### 24.1 프레임워크는 테스트 없이는 설명되기 어렵다

애플리케이션 테스트와 프레임워크 테스트는 닮았지만 목적이 다르다. 애플리케이션 테스트는 기능이 기대대로 동작하는지 확인하고, 프레임워크 테스트는 계약과 경계가 유지되는지 검증한다. 즉, 프레임워크는 기능보다 규칙을 테스트해야 한다.

`spring-lite-test` 모듈은 이런 목적을 보여준다. `@SpringLiteTest`로 컨텍스트를 올리고, mock web 테스트로 디스패치 파이프라인을 검증하며, JDBC 통합 테스트로 트랜잭션과 저장소 동작을 함께 확인한다.

### 24.2 테스트 지원도 프레임워크의 일부다

많은 사람이 테스트 지원을 주변 기능으로 생각하지만, 실제 Spring 생태계에서 테스트 인프라는 매우 중요한 생산성 요소다. 컨테이너를 쉽게 올리고, 웹 요청을 모사하고, 특정 계층만 분리해 검증할 수 있게 해주기 때문이다. `spring-lite`가 최소한의 테스트 지원 모듈을 갖는 것도 단순 편의가 아니라 프레임워크 완성도의 일부다.

### 24.3 무엇을 어떻게 검증할 것인가

이 장은 테스트를 계층별로 나눠 설명하는 편이 좋다.

- 컨테이너 테스트: 등록, 주입, 라이프사이클, 예외 전략
- AOP/트랜잭션 테스트: 프록시 적용, 전파, 롤백 규칙
- 웹 테스트: 매핑, 인자 바인딩, 검증, 예외 응답
- 예제 앱 통합 테스트: 전체 요청 흐름

이 구분을 통해 독자는 프레임워크 검증이 단순 커버리지 올리기가 아니라, 구조적 계약을 층위별로 확인하는 작업임을 이해하게 된다.

### 24.4 Part 6 마무리

Part 6를 마치면 독자는 `spring-lite`가 더 이상 개별 기능의 모음이 아니라 실행 가능한 프레임워크라는 감각을 갖게 된다. JDBC 추상화는 트랜잭션과 맞물리고, 예제 앱은 전체 계층을 연결하며, 부트스트랩 계층은 이 모든 조각을 시작점 하나로 묶는다. 테스트 지원은 그 구조를 반복 가능하게 검증한다. 다음 Part에서는 이제 이 구현을 실제 Spring과 직접 비교하고, 실무 활용과 다음 학습 방향으로 연결한다.
