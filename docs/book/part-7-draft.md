# Part 7 Draft

## Part 7. 실제 Spring과 실무 활용으로 연결한다

마지막 Part의 역할은 두 가지다. 첫째, 지금까지 `spring-lite`로 구현한 구조를 실제 Spring Framework와 Spring Boot의 개념 및 주요 클래스에 정확히 대응시키는 것이다. 둘째, 내부 구조를 이해한 지식을 실무에서 어떻게 판단력으로 전환할지, 그리고 독자가 다음에 무엇을 더 구현하며 배울 수 있을지 제시하는 것이다. 이 Part가 있어야 책이 단순 구현 튜토리얼이 아니라 실무 활용과 지속 학습으로 이어지는 안내서가 된다.

## Chapter 25. `spring-lite`와 실제 Spring Framework 비교

### 25.1 비교는 기능 목록이 아니라 구조 대응이어야 한다

실제 Spring과 학습용 프레임워크를 비교할 때 흔한 실수는 "무엇이 더 많다"는 식의 기능 나열에 머무르는 것이다. 그러나 독자에게 더 중요한 것은 구조 대응이다. `ApplicationContext`에 해당하는 축은 무엇인지, `DefaultListableBeanFactory`가 맡는 책임은 어떤 부분인지, `DispatcherServlet`과 `PlatformTransactionManager`에 대응하는 개념은 어디에 있는지를 매핑해야 한다.

이 장은 그 대응 관계를 분명히 보여줌으로써, 독자가 실제 Spring 소스 코드로 넘어갈 수 있는 다리를 놓는다. 복잡성의 차이를 숨기지 않되, 핵심 골격이 공유된다는 점을 선명하게 유지하는 것이 중요하다.

### 25.2 같은 문제, 더 큰 해법

실제 Spring은 `spring-lite`와 같은 문제를 풀지만, 더 다양한 환경과 더 긴 역사, 더 풍부한 확장을 감당해야 한다. 그래서 추상화 계층이 많고, 설정 조합이 풍부하며, 하위 호환을 위한 장치도 많다. 이 사실을 이해하면 복잡성이 곧바로 과잉 설계처럼 보이지 않는다. 오히려 "학습용 구현이 제거한 비용"이 무엇이었는지를 객관적으로 볼 수 있게 된다.

### 25.3 소스 읽기 가이드와 연결

이 장은 단순 비교에서 끝나지 말고, 실제 Spring 소스 코드를 어디서부터 읽으면 좋은지 안내해야 한다. 예를 들어 컨테이너는 `DefaultListableBeanFactory`, 웹은 `DispatcherServlet`, 트랜잭션은 `TransactionInterceptor`, 부트는 auto-configuration 진입점부터 보라는 식의 흐름을 제시하면 좋다. 그러면 책이 독자의 다음 학습 경로까지 자연스럽게 이어진다.

## Chapter 26. 실무에서 이 원리를 어떻게 써먹을 것인가

### 26.1 원리를 아는 사람은 증상이 아니라 경로를 본다

실무에서 문제를 해결할 때 가장 큰 차이는 어디를 먼저 의심하느냐다. 내부 원리를 모르면 증상만 본다. 예를 들어 트랜잭션이 안 걸린다고 느끼면 데이터베이스부터 의심하고, 빈 주입이 꼬이면 애너테이션을 다시 붙이는 식이다. 반대로 내부 원리를 이해하면 호출 경로, 빈 생성 경로, 설정 조립 경로를 먼저 본다.

이 장의 목표는 그 차이를 독자에게 실감시키는 것이다. 구조를 아는 개발자는 문제를 더 정확히 분해하고, 로그도 더 의미 있게 읽으며, 설정 충돌의 원인도 더 빨리 좁힌다.

### 26.2 자주 만나는 실무 오해들

실무에서 반복적으로 등장하는 주제는 대체로 비슷하다.

- `@Transactional`이 왜 어떤 메서드에서는 안 먹는가
- 빈 생성 실패는 왜 애플리케이션 시작 시점에 한꺼번에 터지는가
- 자동 설정과 사용자 설정은 왜 충돌하는가
- MVC 매핑은 왜 분명해 보이는데도 안 잡히는가
- 프록시 객체 때문에 테스트나 타입 비교가 왜 달라지는가

이 장에서는 이런 질문을 각각 앞선 파트와 연결해 풀어야 한다. 즉, 문제 해결 팁을 나열하는 것이 아니라, "어떤 내부 구조를 떠올리면 이 문제가 설명되는가"를 보여줘야 한다.

### 26.3 설계와 리뷰 관점으로의 확장

원리를 이해하면 디버깅만 좋아지는 것이 아니다. 아키텍처 리뷰나 코드 리뷰에서도 판단 기준이 생긴다. 예를 들어 순환 참조 위험을 더 빨리 감지할 수 있고, 선언형 트랜잭션을 남발하는 구조의 한계를 지적할 수 있으며, 설정 외부화와 빈 조립 정책을 더 깔끔하게 설계할 수 있다. 즉, 프레임워크 이해는 도구 사용법을 넘어 설계 감각과도 연결된다.

## Chapter 27. `spring-lite` 이후 무엇을 더 만들 것인가

### 27.1 학습은 완성보다 확장에서 오래 남는다

책을 마쳤을 때 독자가 얻어야 하는 것은 "이제 끝났다"는 느낌보다 "다음에 어디를 확장해 보면 더 많이 배울 수 있는가"라는 감각이다. 프레임워크를 직접 만들며 배우는 방식의 진짜 장점은, 한 번 골격을 이해한 뒤에는 새로운 기능을 직접 추가하며 학습을 지속할 수 있다는 점이다.

### 27.2 다음 확장 후보들

`spring-lite`의 다음 단계는 이미 비교적 분명하다.

- `@ControllerAdvice` 기반 전역 예외 처리
- 더 풍부한 conversion service
- advisor ordering과 더 정교한 포인트컷
- 조건부 auto-configuration 확장
- profile과 environment 모델 강화
- 이벤트 시스템과 관측성 계층 확장

이 목록은 단순 기능 체크리스트가 아니다. 각 항목은 실제 Spring이 더 복잡해지는 이유를 다시 추적하게 만드는 학습 과제다. 예를 들어 conversion service를 구현하기 시작하면 바인딩과 검증, 설정 값 주입이 모두 더 넓게 연결된다.

### 27.3 독자 과제로 마무리하기

책의 마지막은 가능하면 독자가 직접 손대볼 수 있는 과제로 닫는 편이 좋다. "이 장을 읽고 무엇을 구현해보면 좋은가"가 남아야 책이 수동적 독서에서 끝나지 않는다. 따라서 이 장은 기능 후보를 설명하는 데서 멈추지 말고, 난이도와 학습 효과까지 함께 정리하는 것이 바람직하다.

### 27.4 책 전체 마무리

우리는 이 책에서 Spring을 흉내 낸 것이 아니라, Spring의 핵심 원리를 드러내는 실행 가능한 축소판을 만들었다. 컨테이너가 어떻게 빈을 만들고, 라이프사이클과 후처리기가 어떻게 확장을 가능하게 하며, 프록시와 트랜잭션, MVC와 JDBC, 부트스트랩과 테스트가 어떻게 하나의 런타임으로 이어지는지 끝까지 따라왔다. 이제 독자는 Spring을 더 이상 마법처럼 보지 않을 것이다. 복잡하지만 설명 가능한 구조로 보게 될 것이다.
