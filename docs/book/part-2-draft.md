# Part 2 Draft

## Part 2. IoC 컨테이너를 직접 만든다

Part 2의 목적은 Spring의 출발점이 객체 자체가 아니라 객체 생성과 조립을 관리하는 컨테이너라는 사실을 독자에게 체감시키는 데 있다. 이 파트에서는 `spring-lite-context`를 중심으로, 빈 정의 등록부터 생성자 주입, 컴포넌트 스캔, 설정 클래스, 값 주입, 스코프와 이벤트까지 한 단계씩 쌓아 올린다.

## Chapter 3. 첫 번째 컨테이너: BeanDefinition과 Bean Registry

### 3.1 객체보다 먼저 있어야 하는 것

많은 개발자는 IoC를 "객체를 대신 만들어준다"는 정도로 기억한다. 틀린 말은 아니지만 충분하지 않다. 컨테이너가 실제로 먼저 관리하는 것은 객체가 아니라 객체 생성에 대한 설명이다. 어떤 클래스를 만들지, 어떤 이름으로 등록할지, 어떤 생성 전략을 사용할지 같은 정보가 먼저 있어야 한다. 이 정보가 없으면 컨테이너는 빈을 일관되게 다룰 수 없다.

`spring-lite`에서 이 역할을 맡는 것이 `BeanDefinition`이다. 이것은 단순 DTO처럼 보이지만 컨테이너 설계의 시작점이다. 컨테이너는 곧바로 객체를 만드는 대신, 먼저 "무엇을 어떻게 만들 것인가"를 등록한다. 이 방식 덕분에 컨테이너는 같은 구조 위에서 클래스 기반 빈, 팩토리 메서드 기반 빈, 스캔된 빈을 모두 다룰 수 있다.

### 3.2 Registry와 Singleton Cache는 왜 분리되는가

초기 컨테이너를 설계할 때 쉽게 빠지는 함정은 등록과 저장을 한 곳에 섞는 것이다. 하지만 빈 정의 등록소와 실제 싱글톤 인스턴스 저장소는 역할이 다르다. 등록소는 생성 계획을 들고 있고, 캐시는 이미 만들어진 결과를 들고 있다.

이 둘이 분리되면 여러 장점이 생긴다. 빈 정의를 먼저 모두 수집한 뒤 생성 순서를 제어할 수 있고, 아직 인스턴스가 없더라도 타입 조회나 이름 충돌 검사 같은 작업을 수행할 수 있다. 또한 생성에 실패한 빈을 캐시에 섣불리 남기지 않게 되어 실패 전략도 더 명확해진다.

Spring의 `BeanFactory`와 `BeanDefinitionRegistry` 분리 역시 같은 문제의식에서 나온다. 실제 Spring은 훨씬 더 많은 메타데이터와 후처리 단계를 가지지만, 출발점은 같다. 메타데이터와 실체를 구분해야 컨테이너가 유연해진다.

### 3.3 `spring-lite`에서 보는 최소 컨테이너 구조

`spring-lite-context`의 초기 핵심 구조는 비교적 단순하다.

- 빈 이름을 키로 하는 `BeanDefinition` 등록소
- 생성된 싱글톤 인스턴스를 담는 캐시
- 이름과 타입으로 빈을 조회하는 API
- 빈을 실제로 생성하는 내부 팩토리 메서드

겉보기에는 단순해 보여도, 이 구조만 있으면 이미 프레임워크다운 판단이 가능해진다. 예를 들어 이름 중복을 막을 수 있고, 동일 타입 후보를 수집할 수 있으며, 아직 생성되지 않은 빈도 조회 대상으로 포함할 수 있다. 즉, "컨테이너"라는 말은 결국 생성 정책과 조회 정책을 함께 가진 런타임이라는 뜻이다.

### 3.4 코드로 읽는 핵심 포인트

이 장에서 독자는 [spring-lite-context](../../spring-lite-context)의 `BeanDefinition`과 `DefaultApplicationContext` 초반부를 중심으로 읽게 된다. 중요한 것은 필드 하나하나보다도, 컨테이너가 왜 직접 클래스만 보지 않고 메타데이터 레이어를 두는지 이해하는 것이다. 테스트 코드는 이름 기반 등록, 타입 기반 조회, 중복 등록 실패를 보여주는 최소 사례로 제시하면 좋다.

### 3.5 실무 연결

이 장의 메시지는 단순한 학습용 구현을 넘어 실제 Spring 이해로 이어진다. 실무에서 "왜 이 빈이 등록되었는가"를 파악하려면 결국 메타데이터 관점으로 올라가야 한다. 자동 설정, 스캔, `@Bean` 등록이 모두 빈 정의 단계에서 만나기 때문이다.

## Chapter 4. 생성자 주입과 의존성 해석

### 4.1 DI는 알고리즘이다

생성자 주입은 흔히 가장 권장되는 주입 방식으로 소개된다. 하지만 왜 그런지 제대로 설명하지 않으면 단순 스타일 가이드처럼 보이기 쉽다. 실제로 생성자 주입은 컨테이너 입장에서 가장 분명한 계약을 제공한다. 어떤 의존성이 반드시 필요한지 생성자 시그니처에 드러나고, 객체가 불완전한 상태로 만들어질 가능성도 줄어든다.

다만 컨테이너 입장에서는 생성자 주입이 쉬운 일만은 아니다. 적절한 생성자를 선택해야 하고, 각 파라미터에 대해 후보 빈을 찾아야 하며, 후보가 없거나 여러 개일 때 어떤 예외를 낼지도 결정해야 한다. 즉, DI는 선언 몇 줄이 아니라 해석 알고리즘이다.

### 4.2 생성자 선택 규칙

`spring-lite`는 학습 목적상 예측 가능한 규칙을 우선한다. 생성자가 하나뿐이면 그것을 사용하고, 여러 생성자가 있으면 가장 명확한 선택 기준을 적용한다. 이 기준은 책에서 단순하게 설명할수록 좋다. 중요한 것은 "컨테이너가 임의로 고르는 것이 아니라, 재현 가능한 규칙을 가져야 한다"는 점이다.

실제 Spring은 `@Autowired`, 기본 생성자, 파라미터 메타데이터, 선택 가능 후보 등을 종합해 더 복잡한 판단을 한다. 하지만 학습 초기에는 규칙이 분명할수록 컨테이너의 책임이 잘 보인다.

### 4.3 타입 기반 탐색과 실패 전략

의존성 해석의 핵심은 타입 기반 탐색이다. `OrderService` 생성자에 `OrderRepository`가 필요하면, 컨테이너는 등록된 빈 정의들 가운데 그 타입에 맞는 후보를 찾아야 한다. 여기서 두 가지 실패가 중요해진다.

- 후보가 하나도 없을 때: `NoSuchBeanDefinitionException`
- 후보가 둘 이상일 때: `NoUniqueBeanDefinitionException`

이 예외는 불편한 제약이 아니라 건강한 실패 전략이다. 컨테이너가 모호한 상태를 조용히 넘어가면 문제는 더 늦고 더 복잡한 지점에서 터진다. 실무에서도 "왜 애플리케이션이 빨리 실패해야 하는가"를 설명하는 중요한 근거가 된다.

### 4.4 순환 참조가 왜 곧바로 드러나는가

생성자 주입은 순환 참조 문제를 빨리 드러낸다. `A`를 만들려면 `B`가 필요하고, `B`를 만들려면 다시 `A`가 필요하면 컨테이너는 어느 한쪽도 완성하지 못한다. 이것은 생성자 주입의 단점이 아니라 장점에 가깝다. 구조적 문제를 조기에 노출하기 때문이다.

이 장에서는 순환 참조를 완전히 해결하지 않는다. 대신 "왜 생성자 주입에서 특히 어렵게 드러나는가"를 명확히 설명하고, Part 3에서 실패 전략과 설계 판단으로 이어간다.

### 4.5 코드와 테스트 포인트

독자는 의존성 해석 로직과 관련 테스트를 함께 읽으며, 성공 케이스뿐 아니라 실패 케이스도 같은 비중으로 봐야 한다. 특히 생성자 인자 수가 늘어나도 컨테이너 로직은 같은 패턴을 반복한다는 점, 그리고 타입 기반 탐색이 생각보다 많은 예외 정책을 필요로 한다는 점을 확인하는 것이 중요하다.

## Chapter 5. 컴포넌트 스캔과 메타 애너테이션

### 5.1 수동 등록의 한계

앞선 장들까지는 빈을 명시적으로 등록하는 방식이 이해에 유리하다. 하지만 실제 애플리케이션에서 모든 클래스를 손으로 등록하는 방식은 금방 지친다. 프로젝트가 커지면 객체를 만드는 규칙보다 등록을 놓치지 않는 일이 더 어려워진다. 이 지점에서 컴포넌트 스캔이 등장한다.

컴포넌트 스캔은 단순 자동화가 아니다. "어떤 클래스를 빈 후보로 볼 것인가"를 애너테이션 메타데이터로 표현하고, 클래스패스에서 이를 찾아 등록하는 체계다. 즉, 등록 규칙 자체를 코드 밖으로 끌어올린 것이다.

### 5.2 파일 시스템과 JAR 스캔

스캔은 아이디어는 단순하지만 구현은 금방 현실적인 문제를 만난다. 개발 환경에서는 클래스 파일이 디렉터리에 놓여 있지만, 배포 환경에서는 JAR 안에 있을 수 있다. `spring-lite`가 파일 시스템과 JAR 스캔을 모두 지원하는 이유는, 학습용 프레임워크라도 스캔이 결국 클래스패스 문제라는 사실을 보여주기 위해서다.

이 장은 독자에게 "애너테이션만 보면 되는 것 아니었나?"라는 착각을 깨준다. 실제로는 클래스 로딩 비용, 패키지 경로 해석, 중복 탐색, 메타 애너테이션 처리 같은 문제가 함께 온다.

### 5.3 메타 애너테이션이 주는 표현력

`@Service`와 `@Repository`가 결국 `@Component`처럼 동작하는 이유는 메타 애너테이션 덕분이다. 이것은 단순 문법 설탕이 아니라 도메인 의미를 풍부하게 표현하면서도 동일한 등록 규칙에 얹을 수 있게 해주는 설계다.

`spring-lite`에서 메타 애너테이션 탐색을 구현하면, 애너테이션 모델도 결국 그래프 탐색 문제라는 사실이 드러난다. 동시에 실제 Spring이 왜 조합 가능한 스테레오타입 모델을 오래 유지해 왔는지도 이해하게 된다.

### 5.4 빈 이름 생성과 충돌

스캔이 도입되면 이름 생성 전략도 중요해진다. 클래스명을 그대로 쓸지, 첫 글자를 소문자로 바꿀지, 명시적 이름을 우선할지 같은 규칙이 필요하다. 이 규칙은 사소해 보여도 충돌과 디버깅 비용에 직접 영향을 준다.

이 장에서는 자동화가 늘수록 규칙 설계가 더 중요해진다는 사실을 보여주면 좋다. 프레임워크는 편의를 제공할수록 예측 가능성까지 함께 보장해야 하기 때문이다.

### 5.5 코드와 실무 연결

이 장은 `ClassPathBeanDefinitionScanner`와 스캔 테스트를 중심으로 읽는다. 실무적으로는 "왜 어떤 클래스는 스캔되고 어떤 클래스는 안 되는가", "왜 패키지 기준이 중요한가"를 설명할 수 있게 되면 충분히 성과가 있다.

## Chapter 6. `@Configuration`과 `@Bean`으로 설정 클래스를 다루기

### 6.1 왜 컴포넌트 모델만으로는 부족한가

컴포넌트 스캔이 강력하다고 해서 모든 빈 등록 문제를 해결하지는 못한다. 외부 라이브러리 타입처럼 소스에 애너테이션을 붙일 수 없는 경우도 있고, 생성 과정에서 여러 설정 값을 조립해야 하는 경우도 있다. 이때 필요한 것이 `@Configuration`과 `@Bean` 방식이다.

이 방식의 본질은 "클래스를 빈으로 직접 삼는다"가 아니라 "메서드를 빈 팩토리로 사용한다"는 점이다. 즉, 빈 정의의 출처가 클래스 자체일 수도 있고, 메서드 실행 결과일 수도 있다는 사실을 컨테이너가 받아들여야 한다.

### 6.2 설정 클래스는 왜 특별 취급되는가

설정 클래스는 겉으로 보면 일반 빈처럼 보인다. 하지만 내부적으로는 다른 빈 정의를 추가로 만들어내는 역할을 한다. 그래서 컨테이너는 설정 클래스를 먼저 읽고, 그 안의 `@Bean` 메서드들을 별도의 `BeanDefinition`으로 등록해야 한다.

이 장에서 독자는 "컨테이너도 자신이 처리할 메타데이터를 만들기 위해 먼저 일부 빈을 특별 취급해야 한다"는 사실을 배운다. 실제 Spring의 설정 처리기가 더 복잡한 이유도 여기서 출발한다.

### 6.3 팩토리 메서드 기반 생성 모델

`spring-lite`는 팩토리 메서드 기반 생성을 통해 생성 전략이 클래스 생성자 하나로 고정되지 않음을 보여준다. 어떤 빈은 직접 생성자를 호출해 만들고, 어떤 빈은 설정 객체의 메서드를 호출해 만든다. 이 차이를 메타데이터 레벨에서 다루기 위해 `FACTORY_METHOD` 같은 구분이 필요해진다.

독자가 여기서 얻어야 할 통찰은 단순하다. 빈 생성 전략이 하나만 있는 컨테이너는 금방 한계에 부딪힌다. 실무에서 `@Bean`을 자주 쓰는 이유도 결국 조립 유연성 때문이다.

### 6.4 실제 Spring과의 거리

실제 Spring은 `@Configuration` 클래스에 대해 CGLIB 기반 강화 모델을 적용해 `@Bean` 메서드 간 호출 일관성까지 보장한다. `spring-lite`는 그 전 단계까지만 구현하지만, 왜 실제 Spring이 더 복잡한 선택을 했는지는 충분히 설명할 수 있다. 즉, 학습용 구현의 단순함이 실제 구현의 필요를 가리는 것이 아니라 오히려 선명하게 만든다.

## Chapter 7. `@Qualifier`, `@Value`, 설정 값 주입

### 7.1 타입만으로는 결정할 수 없는 순간

타입 기반 주입은 기본적으로 훌륭하지만, 같은 타입의 구현이 여러 개 생기는 순간 곧바로 모호성이 드러난다. 할인 정책, 메시지 발송 전략, 저장소 구현체 같은 현실적인 예제를 떠올리면 어렵지 않다. 이때 컨테이너는 "어느 빈을 선택해야 하는가"라는 질문을 피할 수 없다.

`@Qualifier`는 이 문제를 해결하는 최소 장치다. 중요한 것은 이것이 이름 매칭 트릭이 아니라, 타입 기반 자동화 위에 사람의 의도를 추가로 얹는 장치라는 점이다.

### 7.2 값 주입은 왜 별도 문제인가

`@Value`는 흔히 간단한 편의 기능처럼 보인다. 하지만 실제로는 외부 설정과 애플리케이션 조립을 연결하는 관문이다. 문자열 플레이스홀더를 해석하고, 설정 소스를 읽고, 필요한 경우 타입 변환까지 해야 한다. 즉, 값 주입은 작은 기능이 아니라 환경 추상화의 시작이다.

`spring-lite`가 YAML 기반 최소 프로퍼티 리졸버를 제공하는 이유도 여기에 있다. 설정 파일은 결국 빈 조립의 입력이다. 이 사실을 이해하면 "설정도 애플리케이션 런타임의 일부"라는 관점이 생긴다.

### 7.3 선택과 외부화가 컨테이너를 확장한다

이 장의 핵심은 컨테이너가 단순 생성기에서 점점 정책 시스템으로 확장된다는 점이다. 타입 우선, qualifier 보조, 프로퍼티 해석, 기본값 처리 같은 규칙이 쌓일수록 컨테이너는 더 많은 결정을 대신 내린다. 생산성은 올라가지만, 동시에 규칙을 설명할 수 있어야 디버깅도 가능해진다.

### 7.4 실무 연결

실무에서 이 장의 효용은 매우 직접적이다. "왜 같은 타입 빈이 여러 개인데 이 구현이 주입되었는가", "왜 설정 값이 비어 있는가", "왜 실행 환경마다 동작이 달라지는가" 같은 질문이 모두 여기와 연결된다. `@Qualifier`와 `@Value`를 사용법이 아니라 의도 표현과 설정 해석의 관점으로 이해해야 하는 이유다.

## Chapter 8. Scope와 컨테이너 이벤트

### 8.1 컨테이너는 살아 있는 런타임이다

지금까지의 컨테이너는 빈을 만들고 보관하는 구조로 보였다. 하지만 실제 애플리케이션은 시작과 종료라는 시간을 가진다. 어떤 객체는 한 번만 만들어 재사용해야 하고, 어떤 객체는 요청할 때마다 새로 만들어야 하며, 어떤 컴포넌트는 컨텍스트가 닫힐 때 정리되어야 한다. 그래서 스코프와 이벤트가 필요하다.

### 8.2 singleton과 prototype

싱글톤 스코프는 컨테이너가 하나의 인스턴스를 캐시에 보관해 재사용하는 방식이다. 반면 프로토타입은 요청할 때마다 새 인스턴스를 만든다. 이 차이는 단순 성능 문제가 아니라 책임 분리 문제다. 싱글톤은 컨테이너가 수명 전체를 관리하지만, 프로토타입은 생성 이후 관리 범위가 줄어든다.

이 장에서는 독자에게 "스코프는 객체 생성 횟수의 문제가 아니라 수명과 책임의 문제"라고 설명하는 것이 중요하다. 그래야 이후 실제 Spring의 request/session/application scope도 자연스럽게 이해된다.

### 8.3 컨텍스트 이벤트의 의미

이벤트는 프레임워크 내부에서 느슨한 연결을 만들 수 있게 해준다. 컨텍스트가 새로고침되었을 때 어떤 초기화 로직을 실행하거나, 종료 시 정리 동작을 수행하는 식이다. `ApplicationListener`와 `ContextRefreshedEvent`, `ContextClosedEvent`는 작아 보이지만 컨테이너를 수동 팩토리와 구분 짓는 중요한 요소다.

이벤트 모델을 도입하면 독자는 "프레임워크는 함수 호출 몇 번의 묶음이 아니라 상태 전이를 가진 런타임"이라는 사실을 받아들이게 된다.

### 8.4 Part 2 마무리

Part 2를 마치면 독자는 이제 컨테이너의 기본 골격을 설명할 수 있어야 한다. 빈 정의를 등록하고, 생성자를 해석하고, 스캔으로 후보를 수집하고, 설정 클래스와 값 주입을 통해 조립 유연성을 확보하고, 스코프와 이벤트로 런타임 성격을 부여한다. 다음 Part에서는 이 컨테이너 위에서 빈 라이프사이클과 확장 포인트가 어떻게 작동하는지 살펴본다.
