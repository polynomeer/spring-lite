# Book Enhancement Plan

이 문서는 `Build Your Own Spring Lite` 원고를 출간 수준으로 끌어올리기 위한 보강 계획 문서다. 목표는 단순 분량 증가가 아니라, 독자가 실제로 구현하고 이해하고 실무에 연결할 수 있는 책으로 다듬는 것이다.

## 1. 현재 강점

- `spring-lite` 코드와 원고가 같은 저장소 안에서 직접 연결되어 있다.
- IoC, AOP, MVC, JDBC, Transaction, Boot, Test를 하나의 런타임 서사로 설명한다.
- build-along 문서와 완성 원고가 분리되어 있어 집필 전개가 명확하다.
- 공식 문서, 대표 서적, 강의, 기술 글의 관점을 원고에 반영하기 시작했다.

## 2. 현재 부족한 점

- 장마다 설명 밀도와 코드 밀도가 일정하지 않다.
- 일부 장은 코드 블록은 있으나 클래스/메서드 구조 해설이 상대적으로 얕다.
- 장 마무리 요약, 디버깅 포인트, 실제 Spring 확장 읽기 가이드가 충분히 통일돼 있지 않다.
- 독자 과제와 체크리스트가 약해 실습서 감각이 덜하다.
- 부록이 더 강한 참고서 역할을 하도록 확장될 여지가 있다.

## 3. 보강 우선순위

### 우선순위 1. 장별 형식 통일

모든 핵심 장이 가능하면 아래 형식을 갖도록 맞춘다.

1. 문제 제기
2. 먼저 실패하거나 기대를 고정하는 테스트
3. 단계별 구현
4. 클래스 구조 해설
5. 메서드 구조 해설
6. 실제 Spring 대응
7. 디버깅 포인트
8. 장 끝 체크리스트

### 우선순위 2. 핵심 클래스 코드 수록량 확대

다음 클래스들은 "핵심 메서드 일부"가 아니라 장에 따라 거의 전체 구현을 수록하는 방향을 검토한다.

- `AnnotationConfigApplicationContext`
- `BeanDefinition`
- `ClassPathScanner`
- `ProxyFactory`
- `AspectBeanPostProcessor`
- `TransactionalBeanPostProcessor`
- `TransactionManager`
- `DispatcherServlet`
- `RequestMappingHandlerMapping`
- `RequestMappingHandlerAdapter`
- `DefaultExceptionResolver`
- `JsonMapper`
- `JdbcTemplate`
- `SpringLiteApplication`
- `SpringLiteTestExtension`

### 우선순위 3. 실무 디버깅 시나리오 확대

각 Part 또는 각 장에 아래와 같은 장애/디버깅 박스를 넣는다.

- 빈 생성 실패
- 다중 후보 주입 충돌
- self-invocation과 트랜잭션 미적용
- 404 / 400 / 500 분기 추적
- rollback-only 전파
- 자동 설정 충돌과 수동 빈 오버라이드

### 우선순위 4. Part 마무리 프레임 강화

각 Part 끝에 아래를 넣는다.

- 이번 Part에서 만든 것
- 아직 의도적으로 생략한 것
- 실무 디버깅 체크 질문
- 실제 Spring에서 이어서 읽을 클래스
- 독자 연습 과제

### 우선순위 5. 부록 강화

추가 가능 항목:

- 용어집
- 애너테이션/추상화 대응표
- 모듈별 파일 인덱스
- 실제 Spring 소스 읽기 순서
- 챕터별 구현 체크리스트

### 우선순위 6. 설계 사유와 반례 밀도 강화

각 장은 "무엇을 구현했는가"보다 "왜 이 구조를 선택했는가"를 더 선명하게 드러내야 한다. 이를 위해 다음 요소를 의도적으로 늘린다.

- 이전 단계 설계의 한계
- 실패 사례 또는 반례
- 선택하지 않은 대안과 그 이유
- 실제 Spring이 더 복잡한 해법을 택한 배경
- 실무에서 이 선택이 드러나는 장애 장면

### 우선순위 7. 실무 연결 서사 강화

각 장 끝 또는 Part 정리에는 독자가 즉시 실무에 대입할 수 있는 질문을 남긴다.

- 이 기능이 Spring Boot 프로젝트에서 흔히 드러나는 증상은 무엇인가
- 로그를 보면 어느 계층부터 의심해야 하는가
- 팀 코드리뷰에서 어떤 설계 냄새로 보이는가
- 운영 장애에서 어떤 메트릭이나 로그와 함께 봐야 하는가

## 4. 출간 품질 기준

출간 수준의 기술서로 보이기 위해서는 단순 설명량이 아니라 설명의 조직 방식이 일정해야 한다. 최소 품질 기준은 아래와 같다.

### 장 수준 기준

1. 장의 첫 1~2쪽 안에 문제 제기가 분명히 드러난다.
2. 독자가 놓치기 쉬운 실패 사례 또는 오해 사례가 최소 1개 이상 들어간다.
3. 코드 블록은 "왜 이 코드가 필요한가"를 먼저 설명한 뒤 제시한다.
4. 핵심 클래스는 책임, 주요 필드, 핵심 메서드, 예외 조건을 함께 설명한다.
5. 실제 Spring 대응 클래스 또는 공식 문서 읽기 경로가 최소 1회 이상 제시된다.
6. 장 말미에는 디버깅 질문 또는 독자 과제가 남는다.

### Part 수준 기준

1. Part 마지막에 요약, 생략한 복잡성, 디버깅 질문, 실제 Spring 읽기 가이드, 연습 과제가 모두 있다.
2. Part 안의 장들이 "문제 제기 -> 구현 -> 확장 -> 실무 해석" 리듬을 공유한다.
3. 그림, 비교표, 테스트가 최소 한 번 이상 핵심 설명 도구로 쓰인다.

### 책 전체 기준

1. 용어가 일관된다. 등록, 생성, 주입, 초기화, 후처리, 프록시 적용, 디스패치, 전파 같은 용어를 섞어 쓰지 않는다.
2. 구현서와 해설서의 균형을 유지한다. 코드 나열이나 개념 요약 어느 한쪽으로 과도하게 기울지 않는다.
3. 학습용 단순화와 실제 Spring의 복잡성을 구분해 설명한다.
4. 독자가 책만 읽고도 `spring-lite`를 재구현하거나 실제 Spring 소스를 읽기 시작할 수 있어야 한다.

## 5. 실행 순서

1. `complete-manuscript.md` 도입부에 독서 전략, 디버깅 렌즈, 용어 사용 원칙을 고정한다.
2. 각 Part 정리 섹션의 형식을 통일하고 누락된 Part 1 정리를 보강한다.
3. 핵심 장에 실패 사례, 실무 오해, 실제 Spring 대응 설명을 추가한다.
4. `build-along-implementation-guide.md`와 모듈 해설 문서에 클래스/메서드 단위 설명을 늘린다.
5. 부록에 용어집, 공식 문서 병행 읽기 경로, 챕터별 복습 장치를 확장한다.
6. 최종 편집 단계에서 코드 블록 위치, 그림 위치, 비교표 밀도를 다시 조정한다.

## 6. 완료 기준

아래 조건을 만족하면 출간본 초안 완성도는 크게 올라간다.

- Part 2~6 모든 핵심 장에 테스트와 구현 코드가 직접 포함된다.
- 주요 클래스의 책임 분해를 독자가 메서드 단위로 설명할 수 있다.
- 각 Part 끝에 요약, 연습, 실제 Spring 확장 읽기 가이드가 있다.
- 디버깅 시나리오가 기능별로 최소 하나 이상 포함된다.
- 완성 원고만 읽어도 설명서이자 구현서 역할을 함께 수행한다.
- 각 장이 실패 사례, 설계 선택 이유, 실무 연결을 최소 한 번 이상 제공한다.
- 부록만 따로 읽어도 코드 탐색, 디버깅, 공식 문서 병행 학습에 바로 활용할 수 있다.
