## Part 5. Web MVC를 직접 구현한다

Part 5의 목표는 HTTP 요청이 어떻게 컨트롤러 메서드 호출로 바뀌고, 다시 응답으로 돌아오는지를 프레임워크 내부 시점에서 설명하는 것이다. 많은 개발자가 Spring MVC를 라우팅 도구처럼 사용하지만, 실제로는 `DispatcherServlet`을 중심으로 한 전략 객체들의 협업이 핵심이다. 이 파트를 통해 독자는 웹 요청 흐름을 더 이상 검은 상자로 보지 않게 된다.

## Chapter 17. `DispatcherServlet`과 Front Controller 패턴

### 17.1 왜 하나의 진입점이 필요한가

웹 프레임워크에서 가장 먼저 결정해야 하는 것은 요청을 어디서 받느냐이다. 요청마다 다른 컨트롤러로 바로 흩어 보내는 방식은 단순해 보이지만, 공통 전처리와 후처리, 예외 변환, 전략 교체가 어려워진다. 그래서 Spring MVC는 `DispatcherServlet`이라는 하나의 중심 진입점을 둔다.

front controller 패턴의 장점은 모든 요청을 일관된 파이프라인에 넣을 수 있다는 것이다. 인증, 예외 처리, 핸들러 선택, 인자 바인딩, 반환값 처리 같은 공통 문제를 중앙에서 조정할 수 있다. `spring-lite`가 이 구조를 작게 재현하는 이유도 여기에 있다.

### 17.2 전략 객체로 분해되는 이유

`DispatcherServlet` 하나가 모든 일을 직접 처리하면 곧 거대한 분기문이 된다. 실제 Spring이 `HandlerMapping`, `HandlerAdapter`, `ReturnValueHandler` 같은 전략 객체로 역할을 분리하는 이유는, 웹 요청 처리도 결국 조합 가능한 정책 시스템이기 때문이다.

이 장에서는 각 전략의 책임을 명확하게 구분해야 한다. 어떤 핸들러를 찾는 일과, 찾은 핸들러를 실행하는 일과, 반환값을 응답으로 만드는 일은 서로 다른 문제다. 이 분리가 보여야 이후 장에서 인자 바인딩과 예외 처리의 위치도 자연스럽게 이해된다.

### 17.3 컨트롤러도 결국 빈이다

웹 계층을 설명할 때 종종 놓치는 사실이 있다. 컨트롤러도 컨테이너가 관리하는 빈이라는 점이다. 즉, 웹 프레임워크는 컨테이너 바깥의 별도 세계가 아니라 그 위에 올라간 확장 계층이다. 이 사실을 분명히 해두면, 왜 컨트롤러도 주입을 받고, 왜 어떤 컨트롤러는 프록시가 될 수 있으며, 왜 애플리케이션 시작 시점에 매핑 정보가 수집되는지가 모두 설명된다.

## Chapter 18. 요청을 컨트롤러 메서드로 바인딩하기

### 18.1 HTTP 요청은 어떻게 자바 호출로 바뀌는가

컨트롤러 메서드를 호출한다는 말은 간단하지만, 실제로는 꽤 많은 해석이 필요하다. 경로를 읽고, HTTP 메서드를 확인하고, 경로 변수와 쿼리 파라미터를 분리하고, 요청 본문을 역직렬화하고, 최종적으로 메서드 인자 배열을 구성해야 한다. 이 장의 목표는 이 변환 과정을 단계별로 드러내는 것이다.

### 18.2 `@RequestMapping` 계열 애너테이션의 역할

`@RequestMapping`, `@GetMapping`, `@PostMapping`은 단순히 URL 문자열을 붙이는 도구가 아니다. 어떤 조건의 요청이 어떤 핸들러 메서드와 연결되는지 설명하는 메타데이터다. 컨테이너는 애플리케이션 시작 시점에 이 메타데이터를 읽어 매핑 테이블을 만들고, 요청이 들어오면 그 테이블을 기준으로 핸들러를 찾는다.

이 구조를 이해하면 "매핑이 안 잡힌다"는 문제도 단순 오타가 아니라 메타데이터 해석 문제로 볼 수 있게 된다.

### 18.3 인자 리졸버와 바디 바인딩

메서드 호출의 핵심 난점은 인자다. `@PathVariable`, `@RequestParam`, `@RequestBody`는 모두 서로 다른 데이터 원천에서 값을 꺼내온다. 따라서 웹 프레임워크는 파라미터별로 적절한 리졸버를 선택해야 한다. 이것이 `ArgumentResolver` 같은 전략이 필요한 이유다.

이 장은 또한 JSON 본문이 단순 문자열이 아니라 객체 바인딩의 입력이라는 사실도 보여준다. type conversion, null 처리, 필수 여부 판단 같은 문제가 함께 등장하기 때문이다.

### 18.4 실무 연결

실무에서 컨트롤러 바인딩 문제는 매우 자주 만난다. 파라미터가 비어 있거나, 타입 변환이 실패하거나, 요청 본문이 모델과 맞지 않거나, 경로 패턴이 엇갈리는 경우다. 이 장의 설명은 그런 문제를 프레임워크 시점에서 추적할 수 있게 만드는 기초가 된다.

## Chapter 19. JSON 직렬화, 응답 모델, 예외 처리

### 19.1 메서드가 값을 리턴한 뒤에도 할 일이 남아 있다

컨트롤러 메서드가 끝났다고 해서 요청 처리가 끝나는 것은 아니다. 반환값을 JSON으로 직렬화할 수도 있고, 상태 코드와 헤더를 직접 지정할 수도 있으며, 예외가 발생했으면 이를 HTTP 응답으로 변환해야 한다. 즉, 컨트롤러는 응답 생성 파이프라인의 한 중간 지점일 뿐이다.

### 19.2 `JsonMapper`와 `ResponseEntity`

객체를 응답 본문으로 보내려면 직렬화 규칙이 필요하다. `spring-lite`의 `JsonMapper`는 그 최소 형태를 담당한다. 한편 `ResponseEntity` 같은 응답 모델은 개발자가 상태 코드, 헤더, 바디를 명시적으로 제어할 수 있게 해준다. 이 둘을 함께 설명하면 웹 프레임워크가 단순 자동화와 명시적 제어 사이의 균형을 어떻게 잡는지 보인다.

### 19.3 `@ExceptionHandler`의 위치

예외 처리는 비즈니스 코드에 섞기 시작하면 금방 지저분해진다. 웹 프레임워크는 이를 컨트롤러 밖으로 끌어올려 HTTP 응답 규칙으로 다루고 싶어한다. `@ExceptionHandler`는 바로 그 요구를 만족한다. 어떤 예외를 어떤 상태 코드와 바디로 바꿀 것인지를 선언하면, 디스패처는 이를 응답 생성 단계에서 적용한다.

이 장은 독자에게 예외 처리 역시 웹 파이프라인의 일부라는 관점을 심어야 한다. 그래야 Part 7에서 실무 디버깅과도 잘 연결된다.

## Chapter 20. 조건 매핑과 검증

### 20.1 실무 웹 프레임워크는 경로만 보지 않는다

현실의 API는 같은 경로라도 콘텐츠 타입, 헤더, 파라미터 조건에 따라 다른 의미를 가질 수 있다. 따라서 요청 매핑은 단순 경로 문자열 비교가 아니라, 여러 조건을 함께 평가하는 규칙 시스템이 된다. `consumes`, `produces`, `headers`, `params`가 중요한 이유가 바로 여기에 있다.

이 장은 독자에게 "매핑도 일종의 정책 해석"이라는 사실을 보여줘야 한다. IoC와 AOP에서 보았던 패턴이 웹 계층에서도 반복된다는 점이 흥미로운 연결이 된다.

### 20.2 검증은 어디에서 일어나는가

`@Valid`, `@NotNull`, `@Min`, `@Size` 같은 검증 애너테이션은 컨트롤러 메서드 본문 안에서 검사하는 것이 아니다. 보통은 메서드 진입 직전, 인자 바인딩이 끝난 시점에서 실행된다. 이것이 중요한 이유는 실패를 비즈니스 예외가 아니라 요청 오류로 다뤄야 하기 때문이다.

`spring-lite`의 검증 모델은 최소한이지만, 그만으로도 "입력 검증은 웹 계층 파이프라인의 일부"라는 사실을 설명하기에 충분하다.

### 20.3 400 응답으로의 연결

검증 실패가 발생했을 때 프레임워크는 이를 적절한 HTTP 400 응답으로 바꿔야 한다. 이 과정은 예외 처리 모델과도 이어진다. 즉, 바인딩과 검증, 예외 변환은 서로 분리된 기능 같지만 실제로는 하나의 요청 처리 체인 안에서 맞물린다.

### 20.4 Part 5 마무리

Part 5를 마치면 독자는 Spring MVC가 단순 라우터가 아니라 요청을 메서드 호출로, 다시 HTTP 응답으로 바꾸는 전략 객체 집합이라는 사실을 설명할 수 있어야 한다. 다음 Part에서는 이 웹 흐름이 JDBC, 예제 앱, 부트스트랩 계층과 결합되며 비로소 "실행 가능한 프레임워크"가 되는 과정을 본다.
