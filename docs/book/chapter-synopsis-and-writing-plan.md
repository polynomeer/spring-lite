# Chapter Synopsis And Writing Plan

## 문서 목적

이 문서는 [책 전체 목차 설계](./book-outline.md)를 실제 집필 가능한 수준으로 내린 작업 문서다. 각 장마다 아래 내용을 함께 정리한다.

- 장이 독자에게 약속하는 학습 성과
- 반드시 설명해야 하는 개념과 서술 흐름
- `spring-lite` 코드베이스에서 함께 다룰 핵심 모듈과 클래스
- 권장 집필 분량과 서술 밀도

분량 계획은 초고 기준 예상치다. 최종 편집 과정에서 예제 코드, 그림, 비교표, 연습 문제 분량에 따라 조정할 수 있다.

## Part 1. 왜 Spring을 직접 만들어봐야 하는가

### Chapter 1. 프레임워크를 사용하는 사람에서 이해하는 사람으로

- 학습 목표:
  Spring을 "API 묶음"이 아니라 "문제를 해결하는 런타임 구조"로 보게 만든다. 독자가 이 책의 구현형 학습 전략을 받아들이도록 만드는 장이다.
- 상세 시놉시스:
  Spring 이전에 애플리케이션이 어떤 문제를 직접 떠안았는지부터 시작한다. 객체 생성 책임, 의존관계 조립, 트랜잭션 경계, HTTP 요청 라우팅, 설정 조합이 왜 반복 비용을 만들었는지 설명한다. 이후 "직접 구현해보면 보이는 것"을 소개하고, `spring-lite`를 통해 어디까지 재현하고 어디서 의도적으로 단순화했는지 범위를 명확히 규정한다. 마지막에는 전체 저장소 구조와 학습 독서법을 안내해 이후 장의 진입 장벽을 낮춘다.
- 연결 코드:
  `README.md`, `docs/architecture/overview.md`, `settings.gradle.kts`, 각 모듈의 `build.gradle.kts`
- 권장 분량:
  10~12쪽, 12,000~14,000자

### Chapter 2. Spring의 큰 그림: IoC, Lifecycle, AOP, MVC, Transaction

- 학습 목표:

- 연결 코드:
  `spring-lite-context`, `spring-lite-aop`, `spring-lite-web`, `spring-lite-jdbc`, `spring-lite-tx`, `spring-lite-boot`, `example-app`

### Chapter 7. `@Qualifier`, `@Value`, 설정 값 주입

- 학습 목표:

- 연결 코드:

  선언형 AOP가 기존 프록시 인프라 위에 올려진 해석 계층이라는 점을 이해시킨다.
- 상세 시놉시스:
  `@Aspect`, `@Before`, `@Around`, `@AfterReturning`을 단순 애너테이션 문법이 아니라 advice 메타데이터 선언으로 설명한다. 포인트컷 매칭이 완전하지 않아도 "선언을 읽어 인터셉터로 바꾼다"는 핵심 구조가 드러나도록 서술한다. 마지막에는 실제 Spring AOP와 `@AspectJ` 지원이 왜 더 많은 파서와 매처를 요구하는지 비교한다.
- 연결 코드:
  `@Aspect` 처리기, advice 해석기, 관련 테스트
- 권장 분량:
  12~16쪽, 14,000~18,000자

### Chapter 15. `@Transactional`은 실제로 어떻게 동작하는가

- 학습 목표:
  가장 널리 쓰이는 선언형 기능을 프록시와 후처리기 관점에서 해부한다.
- 상세 시놉시스:
  `@Transactional`이 메서드 본문을 바꾸는 것이 아니라 프록시 호출 경로를 바꾼다는 점을 먼저 분명히 한다. `TransactionalBeanPostProcessor`가 어떤 빈을 감싸는지, 인터셉터가 begin/commit/rollback을 어떤 순서로 처리하는지 따라간다. self-invocation 문제가 왜 생기는지와 이를 실무에서 어떻게 피하는지도 예제로 설명한다.
- 연결 코드:
  `spring-lite-tx` 전반, 트랜잭션 후처리기, 인터셉터, 서비스 테스트
- 권장 분량:
  12~14쪽, 14,000~16,000자

### Chapter 16. 트랜잭션 전파와 rollback 정책

- 학습 목표:
  선언형 트랜잭션이 정책 시스템이라는 점을 예외와 중첩 호출 중심으로 이해시킨다.
- 상세 시놉시스:
  `REQUIRED` 전파가 호출 그래프에서 무엇을 의미하는지 설명하고, rollback-only 상태가 왜 필요한지 보여준다. `rollbackFor`, `noRollbackFor`가 단순 옵션이 아니라 예외 의미를 바꾸는 규칙이라는 점을 테스트 사례와 함께 설명한다. 마지막에는 실제 Spring의 propagation, isolation, readOnly와 비교해 다음 확장 과제를 제시한다.
- 연결 코드:
  전파 정책, rollback rule 해석, 예외별 롤백 테스트, JDBC 통합 테스트
- 권장 분량:
  12~14쪽, 14,000~16,000자

## Part 5. Web MVC를 직접 구현한다

### Chapter 17. `DispatcherServlet`과 Front Controller 패턴

- 학습 목표:
  Spring MVC의 중심이 단일 서블릿과 전략 객체 조합이라는 점을 이해시킨다.
- 상세 시놉시스:
  요청을 바로 컨트롤러로 보내는 구조와 front controller 구조를 비교해 왜 중간 조정자가 필요한지 설명한다. `HandlerMapping`, `HandlerAdapter`, `ReturnValueHandler`를 분리한 이유를 책임 관점에서 해설한다. 이 장은 웹 프레임워크가 단순 라우터를 넘어 파이프라인이라는 관점을 심는다.
- 연결 코드:
  `DispatcherServlet`, 핸들러 매핑/어댑터/리턴 핸들러 구현, 요청 흐름 테스트

  10~12쪽, 12,000~14,000자

### Chapter 18. 요청을 컨트롤러 메서드로 바인딩하기

- 학습 목표:
  HTTP 요청이 자바 메서드 호출로 변환되는 과정을 단계별로 이해시킨다.
- 상세 시놉시스:
  URI, HTTP 메서드, 파라미터, 바디가 어떻게 핸들러 메서드의 인자와 매핑되는지 차례대로 다룬다. `@RequestMapping`, `@GetMapping`, `@PostMapping`, `@PathVariable`, `@RequestParam`, `@RequestBody`의 의미를 구현 관점에서 재정의한다. type conversion과 handler method 추상화가 왜 필요한지도 함께 설명한다.
- 연결 코드:
  요청 매핑 등록, 메서드 시그니처 해석, 인자 리졸버, 바디 역직렬화, 관련 테스트
- 권장 분량:
  12~14쪽, 14,000~16,000자

### Chapter 19. JSON 직렬화, 응답 모델, 예외 처리

- 학습 목표:
  컨트롤러 리턴값이 HTTP 응답으로 구체화되는 후반부 파이프라인을 이해시킨다.
- 상세 시놉시스:
  객체 리턴, `ResponseEntity`, 예외 발생 상황을 나눠 응답 생성 흐름을 추적한다. `JsonMapper`의 역할, 상태 코드와 헤더 제어, `@ExceptionHandler`가 예외를 응답으로 변환하는 과정을 설명한다. 여기서 "컨트롤러 메서드 호출이 끝나도 웹 프레임워크 일은 끝나지 않는다"는 점을 강조한다.
- 연결 코드:
  JSON 매퍼, `ResponseEntity`, 예외 처리기 등록과 해석, 응답 테스트
- 권장 분량:
  12~14쪽, 14,000~16,000자

### Chapter 20. 조건 매핑과 검증

- 학습 목표:
  실무 웹 계층이 단순 URL 매핑을 넘어 조건 평가와 입력 검증을 수행한다는 점을 보여준다.
- 상세 시놉시스:
  `consumes`, `produces`, `headers`, `params` 조건이 매핑 선택에 어떻게 개입하는지 설명한다. 이어서 `@Valid`, `@NotNull`, `@Min`, `@Size` 기반 검증이 컨트롤러 진입 직전 어느 단계에서 실행되는지 다룬다. 실패를 400으로 변환하는 정책과 실제 Spring MVC의 Bean Validation 통합도 함께 비교한다.
- 연결 코드:
  조건 매핑 평가기, 검증기, 바인딩 실패 처리, MVC 검증 테스트
- 권장 분량:
  12~16쪽, 14,000~18,000자

## Part 6. JDBC, 예제 앱, Boot 계층으로 완성한다

### Chapter 21. `JdbcTemplate`과 데이터 접근 추상화

- 학습 목표:
  반복적인 JDBC 보일러플레이트를 템플릿 패턴으로 줄이는 이유를 이해시킨다.
- 상세 시놉시스:
  순수 JDBC 코드의 반복 구조를 먼저 드러내고, 자원 정리와 예외 전파, connection 재사용이 왜 추상화 포인트가 되는지 설명한다. `JdbcTemplate`과 `RowMapper`를 통해 "가변 부분만 넘기고 나머지는 프레임워크가 처리한다"는 템플릿 패턴을 보여준다. 트랜잭션과 연결이 재사용되는 지점도 함께 해설한다.
- 연결 코드:
  `spring-lite-jdbc` 전반, `JdbcTemplate`, `RowMapper`, `DriverManagerDataSource`, JDBC 테스트
- 권장 분량:
  10~12쪽, 12,000~14,000자

### Chapter 22. 예제 앱으로 모든 계층을 연결하기

- 상세 시놉시스:
  주문 예제 앱을 기준으로 컨트롤러, 서비스, 저장소, 설정, 검증, 트랜잭션이 한 요청 안에서 어떻게 맞물리는지 풀어낸다. 이 장은 새로운 기능 추가보다 "이제 전체를 읽을 수 있는가"를 확인하는 통합 장 역할을 한다. 테스트가 문서적 증거로 어떤 역할을 하는지도 함께 설명한다.
- 연결 코드:

### Chapter 23. `SpringLiteApplication`과 Bootstrapping

- 학습 목표:
  프레임워크를 라이브러리 집합에서 실행 가능한 애플리케이션 플랫폼으로 완성한다.
- 상세 시놉시스:
  사용자가 `run()` 한 줄로 애플리케이션을 띄울 수 있으려면 내부에서 어떤 인프라를 조립해야 하는지 설명한다. `@SpringLiteBootApplication`, 기본 인프라 등록, 내장 HTTP 서버 시작 흐름을 단계별로 해설한다. 이어서 실제 Spring Boot auto-configuration과 starter 생태계가 왜 더 큰 문제를 푸는지 비교한다.
- 연결 코드:
  `spring-lite-boot` 전반, 애플리케이션 엔트리포인트, 내장 서버 연동, 관련 테스트

### Chapter 24. 테스트 지원 모듈과 프레임워크 검증 전략

- 상세 시놉시스:

## Part 7. 실제 Spring과 실무 활용으로 연결한다

### Chapter 25. `spring-lite`와 실제 Spring Framework 비교

- 학습 목표:

- 상세 시놉시스:

### Chapter 26. 실무에서 이 원리를 어떻게 써먹을 것인가

- 학습 목표:
  내부 구조 이해를 디버깅, 설계, 설정 판단 능력으로 전환시킨다.
- 상세 시놉시스:
  `@Transactional` 오해, 빈 생성 실패, 자동 설정 충돌, MVC 요청 매핑 디버깅, 프록시 기반 테스트 문제를 실무 상황으로 재구성한다. 각 문제를 "원리를 모르면 증상만 본다"는 관점에서 설명하고, 내부 동작을 알면 무엇을 더 빨리 판단할 수 있는지 정리한다. 이 장은 독자의 실무 효용 체감을 책임진다.
- 연결 코드:
  트랜잭션, 컨텍스트, 웹 계층의 대표 실패 테스트와 예제 코드, 비교 문서
- 권장 분량:
  10~12쪽, 12,000~14,000자

### Chapter 27. `spring-lite` 이후 무엇을 더 만들 것인가

- 학습 목표:

- 상세 시놉시스:
  아직 구현하지 않았거나 축소된 기능을 기능 목록으로만 적지 말고, "왜 다음 단계 문제인가" 중심으로 설명한다. `@ControllerAdvice`, conversion service, advisor ordering, richer auto-configuration, 이벤트/관측성, profile/environment 확장 등을 우선순위별로 소개한다. 마지막에는 독자가 직접 확장 실습을 설계할 수 있도록 과제 형식의 마무리를 둔다.
- 연결 코드:
  `docs/codex/next-implementation-backlog.md`, `docs/codex/implementation-roadmap.md`, 관련 모듈 확장 지점

  10~12쪽, 12,000~14,000자
