# spring-lite Lab 리디자인 기획안

> 상태: 제안(초안) · 작성일 2026-10-26
> 디자인 시안: [spring-lite Lab 리디자인 캔버스](https://claude.ai/artifact/ARy6mm2paV8FUCHoskzmuE) (비공개, 공유 메뉴에서 공개 범위를 바꿔야 다른 사람이 볼 수 있다)

이 문서는 현재 `visual-lab/`, `visual-lab-app/`의 구현을 전제로 두지 않고, 프로젝트 목표에서 출발해 학습 도구를 처음부터 다시 기획한 결과다. 기존 문서(`docs/codex/visual-lab-*` 등)는 수정하지 않았고, 이 문서는 그 문서들과 독립된 제안으로 읽는다.

---

## 1. 출발점

### 프로젝트 목표 (변하지 않는 전제)

- Spring의 핵심 원리(IoC/DI, AOP, MVC, `@Transactional`, JDBC, Boot)를 **직접 구현하며 이해**한다.
- 100% API 호환이나 운영 수준의 완성도는 목표가 아니다.
- 의도적인 단순화는 숨기지 않고 **실제 Spring과의 차이로 드러낸다**.

### 이번 기획이 푸는 문제

| 문제 | 지금의 경험 | 리디자인의 답 |
| --- | --- | --- |
| 학습 순서가 보이지 않는다 | 랩 4개가 나란히 놓여 있고 어디서 시작할지 스스로 정해야 한다 | 8개 트랙 × 4단계로 구성된 **학습 지도** |
| trace를 "읽기만" 한다 | 완성된 흐름을 위에서 아래로 훑는다 | **예측 → 실행 → 확인** 루프, 단계별 리플레이 |
| 코드와 화면이 떨어져 있다 | 참고 링크로 문서나 클래스 이름만 안내한다 | 이벤트마다 **소스 라인과 상태**(tx depth, 커넥션)를 함께 보여준다 |
| 실패를 체험하기 어렵다 | 롤백 같은 정해진 분기만 볼 수 있다 | 일부러 망가뜨려 보는 **함정 실험실** |
| 비교가 별도 화면에 갇혀 있다 | 비교 대시보드에 가야만 차이를 볼 수 있다 | 모든 실험에 "Boot에서도 실행" 버튼을 둔다 |

### 대상 사용자

1. **Spring을 써 봤지만 내부는 모르는 백엔드 개발자**: "`@Transactional`이 왜 안 먹지?"를 겪어 본 사람
2. **책(`docs/book`)을 따라 구현하는 학습자**: 자기 구현이 맞게 동작하는지 눈으로 확인하고 싶은 사람
3. **스터디 진행자**: 리플레이 녹화를 공유하며 설명하는 사람

## 2. 핵심 학습 루프

모든 트랙은 같은 네 단계를 돈다.

```
1 개념  →  2 구현  →  3 실험  →  4 비교
왜 필요한가   빈칸 채우기    예측·실행·리플레이   실제 Spring과 나란히
```

- **개념**: 짧은 글, 그림 한 장, 핵심 질문 하나. 책 원고의 해당 절로 연결한다.
- **구현**: 실패하는 테스트를 통과시키는 build-along 과제. 학습자의 구현으로 실험을 돌릴 수 있다.
- **실험**: 결과를 먼저 예측하게 한 뒤 실행한다. 예측이 틀리면 리플레이로 원인을 찾는다.
- **비교**: 같은 시나리오를 Spring Boot에서 실행해 결과와 경로의 차이를 짚는다.

전역 요소: 상단 내비게이션, 개념·클래스 검색(⌘K), 런타임 전환(`lite` / `boot`).

## 4. 화면별 명세

시안의 아트보드 번호와 맞춘다.

### 01 학습 지도 (홈)

- **이어서 하기 카드**: 마지막으로 멈춘 트랙과 단계, 다음 행동(예: "예측하러 가기")
- **트랙 그리드**: core, context, aop, tx, jdbc, web, boot, test. 카드마다 4단계 진행 막대를 둔다(완료는 채움, 진행 중은 주황, 남은 단계는 외곽선).
- **학습 루프 설명**: 처음 온 사용자를 위한 네 단계 안내

### 02 요청 리플레이

- **재생 컨트롤**: 이전/재생/다음, 이벤트 타임라인(계층 색으로 구분), 현재 위치 `6 / 9`
- **콜스택**: 현재 이벤트 시점의 호출 스택. 프록시·인터셉터 프레임은 강조한다.
- **소스 패널**: 현재 이벤트에 대응하는 소스 라인 하이라이트, "IDE에서 열기"
- **상태 인스펙터**: tx depth, 바인딩된 커넥션, autoCommit, rollbackOnly
- **DB 스냅샷**: "이 커넥션"과 "다른 커넥션"에서 본 행 수를 나란히 보여줘 미커밋 상태를 드러낸다
- **예측 프롬프트**: 다음 이벤트 직전에 멈추고 결과를 묻는다
- **이벤트 로그**: 번호, 계층, 이벤트, 설명
- **녹화 공유**, **Boot와 나란히**(같은 요청을 두 런타임에서 재생해 정렬)

### 03 빈 그래프

- 의존 그래프: 노드는 빈, 실선은 주입, 점선은 프록시가 원본을 감싸는 관계
- 노드마다 생성 순서 번호와 노출 형태(raw / proxy / @Bean)
- **생성 순서 재생**: 컨테이너 refresh 과정을 순서대로 애니메이션한다
- **순환 참조 만들어 보기**: 의존을 하나 추가해 사이클을 만들고 기동 실패 메시지를 확인한다
- 선택한 빈의 상세(타입, 프록시 방식과 원인, 주입받은 빈)와 생애 단계

### 04 트랜잭션 샌드박스 (시안에서 클릭해 볼 수 있음)

- **호출 구조 편집기**: 메서드 블록을 중첩하고 각 블록의 전파 속성, SQL, 예외, try/catch를 고른다
- **예측**: 객관식(예: "orders 1행 · audit_log 0행"). 고르기 전에는 실행할 수 없다.
- **실행 결과**: 트랜잭션별 타임라인(begin, 보류, 재개, commit/rollback), 테이블별 최종 행 수, 해설
- 결과에서 리플레이로 이어 보거나 Boot에서 같은 결과가 나오는지 확인한다

### 05 함정 실험실

| 실험 | 계층 | 확인하는 원리 |
| --- | --- | --- |
| 같은 클래스 안에서 부르면 `@Transactional`이 사라진다 | aop · tx | 프록시는 외부 호출만 가로챈다 |
| checked 예외는 기본으로 롤백되지 않는다 | tx | 기본 롤백 규칙, `rollbackFor` |
| private · final 메서드는 가로챌 수 없다 | aop | 프록시 방식별 한계 |
| 생성자 순환 참조로 기동이 멈춘다 | context | fail-fast 순환 감지 |
| singleton에 주입한 prototype은 한 번만 만들어진다 | context | 스코프와 주입 시점 |
| 안쪽 REQUIRED 예외를 삼켜도 전체가 롤백된다 | tx | rollback-only 전파 |
| 새 스레드에서는 같은 트랜잭션이 아니다 | tx · jdbc | 스레드에 바인딩된 커넥션 |
| `@Valid`를 빠뜨리면 검증이 일어나지 않는다 | web | 인자 해석과 검증 시점 |

각 실험은 **재현 → 리플레이로 원인 찾기 → 고치고 다시 실행** 순서로 진행한다.

### 06 요청 실행 · 레인 뷰

리플레이 이전 단계로, 요청을 보내고 전체 흐름을 한눈에 본다.

- **질문 목록**: 난이도와 계층 태그, live 지원 여부. 질문을 고르면 시나리오가 정해진다.
- **저장된 실행**: 시나리오, 모드, HTTP 상태. 누르면 리플레이로 연다.
- **요청 입력**: 메서드와 경로, 시나리오(create · validation · not-found · rollback · service-error), product, quantity
- **결과 지표**: HTTP 상태, 트랜잭션 결과, DB 영향
- **레인 뷰**: 열은 단계, 행은 Web · Service · Transaction · JDBC. 트랜잭션은 begin부터 rollback까지 하나의 막대로 그려 경계를 드러낸다.
- **해설 카드**: 여기를 보세요 / 왜 중요한가 / 다음 단계
- **코드로 이어보기**: 관련 클래스로 이동
- 상단에서 static / live 모드를 전환한다.

### 07 런타임 비교

- 주제 전환(di · mvc · tx)과 판정 집계(같음 · 단순화 · 미구현)
- 두 런타임의 연결 상태
- **개념 대응표**: 단계마다 spring-lite 구현, 판정, Spring 구현을 나란히 둔다
- **실행 경로 정렬**: 같은 시나리오의 이벤트를 단계 이름으로 맞춰 세우고, 한쪽에만 있는 단계(예: 동기화 등록, afterCompletion 콜백)는 점선 칸으로 표시한다
- 공부 순서 안내, 차이를 샌드박스에서 직접 만들어 보는 링크

### 08 빈 생명주기와 프록시

빈 그래프에서 빈 하나를 골라 들어가는 하위 화면이다.

- **생애 7단계**: 등록 → 생성자 주입 → Aware → @PostConstruct → BPP 후처리 → 노출 → @PreDestroy. 이전/다음 단계로 이동한다.
- **바뀐 것**: 후처리 전 원본과 후처리 뒤 프록시를 나란히 비교
- **BeanPostProcessor 체인**: 후처리기마다 적용 여부(프록시 생성 / 건너뜀)
- **등록된 빈 표**: 스코프, 노출 형태(raw · proxy · @Bean), 그 이유

### 09 구현 워크스페이스 (고도화)

학습 루프의 "2 · 구현" 단계를 화면으로 만든 것이다. 학습 지도에서 들어간다.

- **과제 설명**: 무엇을 만들지와 성공 조건(예: REQUIRES_NEW 구현)
- **테스트 목록**: 통과 / 실패 / 미실행. 실패한 테스트는 기대값과 실제값을 보여준다. 로컬에서 같은 테스트를 돌리는 Gradle 명령도 함께 표시한다.
- **편집기**: 학습자 브랜치의 대상 파일, 채워야 할 부분 강조, 단계별 힌트(1/3 → 3/3)
- **실행 흐름 비교**: 같은 시나리오를 내 구현과 기준 구현으로 실행해 이벤트를 나란히 세우고, **처음 갈라지는 지점**을 표시한다. 테스트가 "틀렸다"만 알려준다면, 이 비교는 "어디서부터 다르게 움직였는지"를 알려준다.

### 10 What-if 스위치 (고도화, 시안에서 클릭해 볼 수 있음)

프레임워크 내부의 핵심 장치를 하나씩 꺼 보고 같은 시나리오의 결과가 어떻게 달라지는지 본다. 장치가 왜 필요한지는 그것이 없을 때 가장 잘 보인다는 생각에서 출발했다.

| 스위치 | 모듈 | 원래 결과 | 켠 뒤 결과 |
| --- | --- | --- | --- |
| rollback-only 표시 무시 | tx | 전체 롤백 | 실패한 작업 일부가 커밋됨 |
| 후처리기 순서 뒤집기 | context · aop | 어드바이스가 트랜잭션 바깥 | 어드바이스가 트랜잭션 안 |
| 인터페이스 프록시 → 클래스 프록시 | aop | 구현 타입 주입 실패 | 주입 성공, final 메서드는 통과 |
| 순환 참조 감지 끄기 | context | 경로를 담은 BeansException | 원인 불명의 StackOverflowError |

- 각 스위치는 바뀌는 코드 한 줄(diff), 시나리오, 전후 결과, "그래서 이 장치가 있다" 해설을 보여준다.
- 두 결과를 리플레이로 나란히 보거나, Spring은 같은 문제를 어떻게 막는지 비교 화면으로 이어진다.
- 시안의 diff 줄은 설명용 예시다. 실제 구현에서는 프레임워크 코드에 실험용 플래그(예: 시스템 프로퍼티)를 두고, 기본값은 언제나 "켜짐"으로 둔다.

### 11 복습 노트 (고도화)

- **오늘의 복습**: 틀렸던 예측에서 만든 질문 카드. 답을 떠올린 뒤 펼친다. 간격 반복으로 다음 복습일을 정한다.
- **약한 개념**: 틀린 예측과 연결된 개념, 그 개념을 다시 볼 수 있는 실험으로 바로 이동
- **예측 기록**: 실험, 내 예측, 실제 결과, 맞음/틀림, 리플레이 링크. "틀린 것만" 필터
- **스터디로 공유**: 리플레이 이벤트마다 메모를 달아 링크 하나로 묶는다. 받은 사람은 메모가 있는 지점에서 멈춘다.
- 기록은 기본적으로 브라우저에만 저장한다(8절 열린 질문 참고).

## 5. 기능 목록과 구현 상태

현재 코드 기준으로 상태를 표시했다. "신규"는 아직 없는 기능이다. 목표에 부합하므로 이 기획에는 우선 포함했다.

### 5.1 학습 도구(프론트엔드)

| 기능 | 상태 | 비고 |
| --- | --- | --- |
| 학습 지도와 트랙별 진행도 | 신규 | 진행도는 우선 브라우저 로컬 저장 |

### 5.3 관측(trace) 인프라 — 신규

리플레이, 상태 인스펙터, 예측 루프가 공통으로 기대는 기반이다.

- **`TraceEvent` 스키마**: `seq`, `layer`(web/service/tx/jdbc/container/aop), `kind`, `marker`, `thread`, `txDepth`, `connectionId`, `stack`(프레임 목록), `source`(파일·라인), `payload`
- **`TraceRecorder`**: 요청 단위로 이벤트를 모으는 수집기. 코어 모듈 의존을 늘리지 않도록 각 모듈의 기존 확장 지점(`BeanPostProcessor`, `MethodInterceptor`, `TransactionManager`, `JdbcTemplate`, `DispatcherServlet`)에 훅을 다는 방식으로 설계한다.
- **DB 스냅샷 API**: 특정 이벤트 시점에 트랜잭션 커넥션과 별도 커넥션으로 각각 행 수를 조회한다
- **시나리오 DSL**: 샌드박스의 호출 구조(메서드, 전파, SQL, 예외, catch)를 JSON으로 받아 실행하는 엔드포인트
- **Boot 쪽 어댑터**: `comparison-spring-boot-app`에서 같은 스키마로 이벤트를 내보낸다. 단계 이름은 정규화해서 맞춘다.

> 의존 방향 원칙(ADR 0001)을 지키기 위해, 이벤트 타입은 `core`에 두고 수집 훅은 각 모듈의 `support` 패키지에 두는 방안을 우선 검토한다. 외부 라이브러리는 추가하지 않는다.

## 6. 디자인 원칙과 토큰

- **색은 장식이 아니라 계층을 가리킨다**: web 파랑, service 초록, tx·proxy 주황, jdbc 보라
- **성공은 채움, 오류는 외곽선**: 색을 구분하기 어려워도 상태를 읽을 수 있게 한다
- **코드 패널은 별도 면으로 구분한다**: 테마와 같은 밝기를 쓰되, 배경 톤과 테두리로 읽는 영역과 실행 화면을 나눈다
- **모든 텍스트 대비 4.5:1 이상**, 터치 대상 44px 이상, 좁은 화면에서는 패널을 세로로 쌓는다

### 테마

테마는 두 가지다. 모든 화면은 같은 토큰 이름(CSS 변수)만 쓰고, 테마가 토큰 값을 바꾼다.

- **light · Lab Notebook (기본)**: 밝은 바탕, 잉크색 글자, 밝은 코드 패널
- **dark · Trace Ink**: 이전 spring-lite Visual Lab 시안의 그린 계열 다크 팔레트

시안 캔버스의 왼쪽 절반은 라이트, 오른쪽 절반은 다크 버전이다. 화면마다 Tweaks의 `theme` 값으로도 전환할 수 있다.

| --- | --- | --- | --- |

## 7. 단계별 로드맵 제안

1. **관측 기반**: `TraceEvent` 스키마, `TraceRecorder`, 기존 example-flow 시나리오를 새 스키마로 내보내기
2. **리플레이**: 스크러버, 콜스택, 상태 인스펙터, 소스 라인 연결
3. **예측 루프와 샌드박스**: 시나리오 DSL, 전파 속성 확장(`MANDATORY` 등)
4. **빈 그래프**: 컨테이너 refresh 이벤트, 순환 참조 실험
5. **함정 실험실**: 실험 8종의 시나리오와 고친 버전
6. **학습 지도**: 트랙과 단계 메타데이터, 진행도, 책 원고 연결
7. **비교 확장**: 모든 실험에 Boot 이중 실행
8. **고도화**: 구현 워크스페이스, What-if 스위치, 복습 노트 (9절)

각 단계는 독립적으로 배포할 수 있고, 1단계가 나머지 모두의 전제다.
